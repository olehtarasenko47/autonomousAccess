# ZoneGuard — failure detection and risk propagation

## Installation

Apply this update on `testmain` (the base is `zoneguard_three_nodes.zip` plus the Windows UDP fix). Replace `main.py`, `peer_state.py` and `telegram_alerts.py`; add `fallback.py`, `test_fallback.py` and this guide. Do not change calibration files, camera credentials or the current databases. SQLite creates the new tables automatically. Upgrade all three laptops together; old clients do not understand the extra incident messages.

Run `python test_access.py` and `python test_fallback.py` (use the virtual-environment Python on Debian). Commit only the six update files and push; teammates pull after stopping their applications.

## Semantics

- Camera loss: after roughly one second without a frame after a working stream (five seconds grace on startup), the node marks its camera offline. It preserves the last processed frame timestamp (UTC), visible role counts, confirmed violation count and most recent observed violation timestamp. It sends a heartbeat immediately, and its durable incident is gossiped. Recovery is recorded after a new processed frame. No stale counts are claimed to be current.
- Node loss: after five seconds without a heartbeat from a previously seen node (15 seconds for a node never seen), the remaining nodes mark it unreachable. A preferred witness records the outage and shares the last replicated snapshot. A backup witness can report if the preferred one is also unreachable. The reporter records recovery when it receives heartbeats again. An unreachable node may be alive but partitioned; a dead node cannot send a final message.
- `TRESPASSING` is the existing confirmed **colour-policy violation**, not proof of criminal trespass. Existing `decision=violation` events remain immutable. Snapshots also expose the current/last observed number of violations and timestamp. `review` is not a confirmed violation.
- `POTENTIAL_TRESPASSING`: an unavailable Zone B (camera offline or peer heartbeat missing) whose last processed observation contained a confirmed colour-policy violation raises an advisory for Zone C. It has no expiry. It clears when B is reachable and supplies a fresh processed camera observation; a heartbeat alone does not clear it. A live B violation is still recorded and notified normally, but does not by itself activate the fallback advisory. If C independently detects a violation its red alert takes display precedence. Historical events remain in SQLite. The deterministic advisory ID identifies the last observed snapshot, so losing the camera and then the laptop does not repeat the same advisory. This assumes B→C adjacency. No individual movement is inferred. `--risk-window 0` disables the advisory; positive values are accepted for compatibility but no longer specify a timeout.
- Telegram health messages are separate from access alert cooldowns and zone mutes. Potential-risk messages respect zone mutes. Originating nodes normally send their own camera or risk notifications. A surviving witness sends node-outage notices, and can send risk notices when the origin is unreachable and no queued-notice mark was replicated. Queued-notice marks suppress replicated duplicates. This is best effort: a partition or crash between queueing and replication can produce duplicates, and a queued notice is not proof Telegram delivered it. Notification queues remain local and retry upon Internet recovery. No photos are attached to health/risk notices.
- Peer loss detection is a local inference, not a consensus protocol. Heartbeat times use monotonic time locally; UTC observation times use the originating laptop clock. Synchronise system clocks. No global state can remain perfectly current during partition. The outage snapshot can be up to approximately one heartbeat interval old (or older if packets were lost). Restarting or partitioning observers can affect the timing of notices.

## Run

Use the existing camera password, peer key, Telegram token and chat environment variables in the same shell. Enable Telegram on all nodes, and `TELEGRAM_LISTEN=1` on Debian only; other nodes set it to 0. Restricted nodes still require all four valid role profiles before `--telegram` is accepted.

- Debian: `python main.py --node node_1 --peer 10.249.42.149 --peer 10.249.47.192 --telegram --cooldown 10`
- Ihor (Windows): `python main.py --node node_2 --peer 10.249.34.231 --peer 10.249.47.192 --telegram --cooldown 10`
- Windows node 3: `python main.py --node node_3 --peer 10.249.34.231 --peer 10.249.42.149 --telegram --cooldown 10`

The port remains UDP 50565. No video is exchanged between peers. Existing `p` prints status including last observations, stale counts, violation flags and risk flags. Telegram `/status` displays the same data.

## Live demonstration

1. Start all three; verify Nodes 3/3. Ensure Zone C is clear. Have a consenting purple-shirt participant enter the monitored Zone B. Wait for the confirmed violation. Confirm Zone B red flag and Telegram access alert, without a fallback advisory while B is healthy. Check `p` on all nodes.
2. Stop Camera 3 streaming **without closing its laptop application**. Verify node 2 remains reachable, camera is offline, previous snapshot is stale, and the Telegram camera-offline alert includes the last observation. Verify the amber potential risk in C and its Telegram alert. Restart the phone stream and verify camera recovery and removal of the advisory after a fresh processed frame.
3. Close node 2's application (or press `c` to simulate peer loss while keeping inference running). After about five seconds, node 1/3 show two reachable nodes and a node-unreachable incident, including the last received snapshot. The other cameras keep working. Restart node 2 (or press `c` again), verify 3/3 and recovery notice.
4. Have a hacker enter C. C displays a confirmed violation instead of the upstream advisory. No correlation of individual people is claimed. Leave B unavailable for longer than 120 seconds to verify the advisory does not expire; restore the camera and verify that it clears only after fresh observations.

## Snapshot evidence and automatic status update

Install the update on all three nodes and `python -m pip install -r requirements.txt` (adds cryptography for AES-GCM). Run `python -m unittest test_access test_fallback test_snapshots` (22 tests). Calibration files and prior event databases are preserved. A new SQLite table stores only the latest JPEG per camera. Do not commit runtime databases, images, outbox data, or secrets.

Start all three nodes with the usual node and peer arguments plus `--telegram --telegram-photos`. Set the same strong, private `ZONEGUARD_PEER_KEY` on all machines, and configure Telegram credentials as before. Keep only one command listener (`TELEGRAM_LISTEN=1`). Photo mode requires organiser approval and an appropriate private Telegram chat. Without `--telegram-photos`, alerts are text only and peer JPEG transport is disabled. All three nodes must enable photo mode to exchange cached evidence. Previously queued photos may still be delivered when Telegram resumes; remove obsolete private data in accordance with the team's retention policy.

- Confirmed local access violations queue a fresh annotated preview, one per Gate event, even when a different violation occurred within the Telegram cooldown. Muting a zone still suppresses its violation notifications; continued presence is deduplicated by the Gate. Review/uncertain classifications remain review events, not confirmed trespassing notifications.
- Every two seconds the source laptop captures an annotated still and gossips the latest still to its two peers. New violations and camera-loss transitions flush a snapshot immediately. Images are compressed to at most 24 KiB, resized to fit within 640 pixels, AES-GCM encrypted with a key derived from the shared peer key, and sent in HMAC-authenticated UDP chunks. Receiver assembles out-of-order chunks and verifies integrity. The latest cached image is persistent, but not an archival recording. No raw video is sent between laptops. The shared peer key protects transport, not the SQLite files at rest.
- Press `c` to capture and transmit the last processed frame and heartbeat before pausing peer communication. The node still processes its camera and can reach Telegram if internet is available. A surviving witness sends the `NODE_UNREACHABLE` notification after heartbeat timeout (normally about five seconds) with the latest cached image. Press `c` again to reconnect. An actual power/network failure cannot transmit a final frame; its most recent successfully replicated still is used. No extra immediate Telegram message from the intentionally paused node is needed.
- `CAMERA_OFFLINE`, `NODE_UNREACHABLE`, and `POTENTIAL_TRESPASSING` include the latest cached evidence from the relevant source if available at or before the incident's observation time. Potential risk for Zone C uses Zone B's image, not Zone C's. All such captions identify the source camera node and original UTC observation time, and say STALE/not live. If no suitable image exists or UDP chunks were lost, the notification still sends as text. Recovery events send text; the previous risk expiry remains disabled and risk clears when the upstream node is reachable with fresh camera data.
- `p` remains an on-demand status dump. Automatic status prints every ten seconds by default, immediately on camera/peer connectivity or trespassing/risk changes (checked every 0.5 s in the processing loop). `--status-interval 5` changes the periodic rate; `0` disables periodic prints but preserves change reports. `/status` in Telegram uses the same state. The camera preview is continuously updated; it does not depend on pressing `p`.

Live acceptance: show a confirmed violation in B, wait for a cached frame to reach both peers, press c on B, and verify one outage notification with stale B evidence and the potential-risk alert with B evidence. Confirm risk stays until B is back and processes new frames. Then unplug a camera without stopping its laptop; verify the camera-offline photo. Finally, close one application entirely and verify surviving peers can deliver its cached image. Live Telegram, real eduroam packet delivery, and camera inference need verification on your actual hardware. In a network partition, occasional duplicate notices or an older/missing cached image remain possible; the last image is not evidence of what happened after the outage.
